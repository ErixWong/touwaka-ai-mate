# Topic 情节化改造（近期主线）

> **状态：计划稿（2026-10-04），经三轮设计评审 + 一次独立代码验证。**
> 关联：[memory-model.md](./memory-model.md)（远期记忆层地图，当前不排期）。
> 本文替代原方案中的"记忆系统 v1"，成为当前唯一排期主线——因为它是唯一有
> **用户实测反馈**（topic 提炼效果不好）支撑的方向。

---

## 1. 诊断（已验证，附代码证据）

### 1.1 当前并存三条 topic 路径，边界标准互不相同

| 路径 | 边界依据 | 摘要生成 | 证据 |
|---|---|---|---|
| 在线聊天建 topic / 语义切换 | **LLM 判定**话题切换 | 建议标题 | `lib/chat-service.js:1398-1433,1456-1526`；`lib/topic-detector.js:37-94` |
| active topic 压缩 | **机械**：消息数 ≥ 50 或 token ≥ 0.7×context | 单次 LLM `summarizeConversation` | `lib/memory-system.js:564-614,636-724,1186-1300` |
| legacy 未绑定消息压缩 | 机械阈值触发 + `identifyTopics` 语义分段（startIndex/endIndex） | 单次 LLM | `lib/memory-system.js:793-880,925-1005` |

### 1.2 问题清单

| ID | 问题 | 证据 |
|---|---|---|
| P1 | **同一个 `Topic` 承担三种职责**（聊天线程 / 归档块 / 检索单元），三条路径边界与质量标准不一致 | 上表 |
| P2 | 质量评估是**形状指标**（字段填没填、长度、关键词数），幻觉摘要也能满分；且**只打日志**、不 gate、不重试 | `lib/memory-system.js:18-70,665-682` |
| P3 | 摘要实际存 `description`（**无 `summary` 列**）；Psyche 自动注入只有 `title + relevance` → 摘要不自动进上下文（但 recall 可取回 `description/keywords` 与原消息） | `models/topic.js:5-94`；`lib/psyche/psyche-model.js:139-150`；`lib/tool-manager.js:2275-2333` |
| P4 | 归档复核器**只扫 active topic**，被压缩归档的 topic 永不复核；识别出"该拆分"时**只打日志，split 是 TODO** | `lib/topic-archiver.js:213-220,245-280` |
| P5 | `detectTopicBoundaries` **已实现但从未接线** | `lib/topic-detector.js:148-183`（全仓无调用） |
| P6 | 压缩在**请求路径被 `await`** → 每轮压缩都在首字节前加一次 LLM 摘要延迟 | `lib/chat-service.js:546-554,660-667,733-749` |
| B1 | 压缩锁按 `expert:user` 加锁、**不带 task** → 不同 task 互相串行 | `lib/memory-system.js:504-514` |
| B2 | 归档器按 expert/user 分组、**不按 task** → 可能因另一个 task 的 topic 数量而归档当前 task 的 topic | `lib/topic-archiver.js:263-280` |
| B3 | `keywords` DDL 为 JSON、生成模型为 TEXT，两者不一致 | `scripts/init-database.js:283`；`models/topic.js:57-61` |

### 1.3 根因

**不是"缺向量"，而是职责混用**：同一个 `Topic` 同时是聊天线程、归档块和检索单元，
所以"什么时候切""摘要写什么""质量怎么算"三条路径各有一套标准，合起来就是检索不准、
内容不够、质量无人管。

> 注：原诊断中"topic 本质是压缩产物"的表述**不准确**——在线聊天与语义切换路径
> 并不由压缩驱动。已按验证结论修正为上述职责混用。

## 2. 基线（先测再改）

**在动任何代码之前建立基线**——否则无法判断改动是变好还是漂移。

| 指标 | 测量方法 | 用途 |
|---|---|---|
| **边界准确率** | 抽样 N 个 topic，人工判定"是否只含一个话题"；统计错误类型（该拆未拆 / 该并未并） | 决定是否需要 re-segment |
| **摘要主张支持率** | 每个 topic 从 `description` 抽 3 条关键主张，回原文区间验证是否被支持 | 替代形状指标，可证伪 |
| **检索命中率** | 构造 M 个真实历史查询，看现有 recall / SQL 搜索（title/description/keywords）top-K 是否命中 | **决定是否需要 embedding** |

产出：三项数字 + 结论（是否存在语义召回缺口）+ 标注样本存档（供改造后对比）。

## 3. 阶段计划（含闸门）

```
⓪ 基线测量（本计划第 2 节）
     ↓ 闸门：检索命中率是否暴露"语义召回缺口"？
① 修既有资产（不新建管线）
     · 归档复核器覆盖范围扩到 archived topic（补 P4 盲区）
     · 实现 split（重分段 + 重摘要），触发标准由 ⓪ 的边界错误样本决定
     · 加修订历史（保留旧摘要/依据消息集合/模型与提示版本/修改原因）
     ↓ 闸门：基线中"摘要不自动进上下文"是否造成实际漏检？
② 注入 description（而非仅 title）——先验证 recall 已用是否够用
     ↓ 闸门：⓪ 是否证明语义召回不足？
③ 仅当 ⓪ 明确暴露语义召回缺口 → 给 `topic` 加 embedding 列（几十条量级，内存 cosine，不建新表）
```

**关键纪律**：每阶段的启动由上一阶段的实测数据触发，不按设计完整度推进。

## 4. 验收与止损

- **验收**：三项基线指标在改造后复测，边界准确率与摘要支持率提升、检索命中率不降；
  改造引入的 split 不产生主题碎裂（同一话题被切成多段）反向指标。
- **止损**：若 ⓪ 显示三项指标本就达标，则**本计划只做 P2/P4/P6 的工程修复，不做结构改造**；
  若 ② 之后命中率已达标，**③ 不启动**。
- **不阻塞的独立项**：B1/B2/B3 是明确缺陷，可并行修复，不等待基线。

## 5. 明确不做

- **不新建"睡眠/整理"管线**——复用并补全既有 `lib/topic-archiver.js`。
- **不建 `message_embedding`**——对消息做向量检索粒度错配（噪声、与活跃窗口冗余、热路径成本），已否决。
- **不建 lesson / pattern / 梦**——见 [memory-model.md](./memory-model.md)，由本计划基线数据触发后才排期。
