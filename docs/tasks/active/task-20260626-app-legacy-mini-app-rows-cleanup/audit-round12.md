## 5. 新增问题与缺口

### 5.1 P1：`changelog_round11.md` 的验证结论与实际 grep 事实不一致，审计记录准确性不足

- **级别**：P1
- **位置**：
  - `docs/tasks/active/task-20260626-app-legacy-mini-app-rows-cleanup/changelog_round11.md:159`
  - `docs/tasks/active/task-20260626-app-legacy-mini-app-rows-cleanup/changelog_round11.md:160`
  - `docs/tasks/active/task-20260626-app-legacy-mini-app-rows-cleanup/changelog_round11.md:161`
- **事实**：文档写明对 `audit-round08.md` 和 `audit-round11.md` 的 `[缺字]` 检索“仅剩审计报告自身对乱码原文的引用”，但当前实际检索结果显示 `audit-round11.md` 还存在多个整改指令中的 `[缺字]` 文字模式，而不仅仅是“原文引用”。
- **影响**：
  1. 审计响应中的“验证通过”结论不可直接采信；
  2. PM 和后续审计人需要重新人工判断哪些 `[缺字]` 属于保留引用、哪些属于验证口径失真；
  3. 放行证据链出现新的可信度折损。
- **判断**：这是当前最需要优先修正的缺陷之一，因为它直接伤害“验证记录可复核性”。
- **技术本质**：不是乱码修复失败，而是**验证口径和实际检查结果没有严格一致**。

### 5.2 P1：Round 11 的工作树范围对账数字前后冲突，边界对账仍不可靠

- **级别**：P1
- **位置**：

## 7. 新一轮变更计划（明确、可衡量、含技术指导）

> **执行总原则**：下一轮不要再把目标定义成“继续补文档”，而要定义成“把审计证据链本身做成可机读、可复核、可追溯”。

### P1-1：重做 Round 11 的验证记录，使“检查命令 → 实际结果 → 结论”完全一致

- **优先级**：P1
- **理由**：当前最大问题不是有没有执行检查，而是文档声称的检查结论与实际仓库事实不完全对应。
- **完成标准**：
  1. 逐条重跑 `changelog_round11.md` 中列出的验证命令对应检查；
  2. 对每条结果写清“无匹配 / 有匹配但属于保留引用 / 有匹配且需整改”；
  3. 不再使用“仅剩……”这类容易掩盖边界的概括性表述，必要时明确列出文件名和匹配类别；
  4. 审计人员按文档步骤复查时，结果不再出现偏差。
- **技术指导**：
  - 验证记录要区分“原文引用保留”与“正文残留缺陷”；
  - 对 `[缺字]` 这类模式，建议分开列“历史引用允许名单”和“非允许匹配即缺陷”；
  - 不要把整改建议中的示例文本误记为“已清理后无匹配”。

### P1-2：重做工作树范围对账，并增加总数自校验

- **优先级**：P1
- **理由**：团队已把“工作树边界清晰”写进放行前提，但当前对账数字仍互相冲突，属于直接破坏放行判断的问题。
- **完成标准**：
  1. 以当前 `git status --short` 为基线列出全部改动路径；
  2. 每个路径标注“属于本任务 / 属于其他任务 / 无法判定”；
  3. 文档中列出的分类数量与总数必须相等，并在文末写出计算式；
  4. `README.md` 与对应 changelog 使用同一版数字，不允许一个写 19、一个写 20。
- **技术指导**：
  - 推荐先出原始清单，再做分类表；
  - 在文档里显式写“总数 = 本任务 X + 其他任务 Y + 待判定 Z”；
  - 统计完成后再写结论，避免先写结论后补表格。

### P2-3：建立“历史审计报告勘误规则”，停止直接重写旧审计正文

- **优先级**：P2
- **理由**：历史审计记录的可信度，来自时间顺序清晰和正文尽量不变。
- **完成标准**：
  1. 在任务文档中增加一条规则：历史 `audit-round*.md` 原则上不直接改正文；
  2. 若确需修正编码问题或明显损坏，需在新一轮 changelog 或 audit 中明确记录“勘误原因、范围、是否影响原结论”；
  3. 后续轮次不再把“修改旧审计正文”当作常规动作。
- **技术指导**：
  - 优先新增 `errata`/“勘误说明”段落，而不是覆盖原判断；
  - 对确实无法阅读的编码损坏，可做最小修复，但必须保留修订说明。

### P2-4：同步任务生命周期状态与目录流转状态

- **优先级**：P2
- **理由**：当前 `README.md` 已写“已完成”，但任务目录仍在 `active`，流程含义不够清晰。
- **完成标准**：
  1. 明确本任务当前属于“active-待复审”还是应转入 `review`；
  2. 在 `README.md` 或 `BRANCH.md` 记录当前阶段说明；
  3. 当 P1 清零后，再执行正式流转，不再让“已完成”与“active”长期并存。
- **技术指导**：
  - 若本项目当前仍采用 `active` 承载多轮审计，可在文档中显式写“已完成待审计归档”；
  - 若已满足 review 条件，则尽快按目录规范推进流转，避免状态口径再次漂移。

### 7.1 建议按 3 个执行包推进

#### 执行包 A：验证记录纠偏

- **目标**：把所有“验证通过”类结论改成可复跑、可核对、可追责的检查记录。
- **通过标准**：审计人员重复执行相同检查时，不会得到与文档相反的结论。

#### 执行包 B：范围对账复算

- **目标**：让“工作树范围清晰”从口头判断变成数字一致的事实表。
- **通过标准**：总数、分类数、路径清单三者完全一致。

#### 执行包 C：审计记录治理规则补齐

- **目标**：明确历史审计文档如何勘误、如何保留时序证据。
- **通过标准**：后续轮次不再直接重写旧审计正文，审计链条保持可追溯。
