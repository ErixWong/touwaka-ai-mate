# 第一轮审计报告：Contract Mgr v2 独立架构收口

## 1. 结论摘要

- **当前整体项目进度**：`contract-mgr-v2` 已完成一部分关键独立化动作，综合进度评估为 **约 55%**；当前处于“主路径切换已启动，但运行时装配、文档平台主链路接入、权限语义与任务留痕尚未完全闭环”的阶段。
- **当前修复方向是否正确**：**正确**。团队已经明确将 `contract-mgr-v2` 视为独立架构 app，开始把版本建档从 `mini_app_rows` / `mini-app.service.js` 中剥离出来。
- **能否满足当前任务目标**：**暂时不能**。目前虽然新增了 `createVersionFromAttachment` 相关代码，但运行时装配链、文档平台接入主链路、API 主路径一致性和任务留痕还没有全部收口。
- **是否引入新的问题和缺口**：**有**，主要集中在运行时路由未完全挂载、前后端路径混合、权限语义不完整、重复控制器层并存，以及“产品闭环尚未真正建立”等方面。
- **本轮结论**：**补充变更点继续**。

---

## 2. 第一性原理与项目全局判断

### 2.1 第一性原理：这件事的本质是什么

从第一性原理看，`contract-mgr-v2` 本轮工作的本质不是：

- 路由是不是放到 app 目录
- controller 应不应该继续保留
- 是否还引用了某个旧 helper

真正的本质是：

1. **用户上传合同后，系统能不能接住**；
2. **合同能不能进入文档平台处理链路**；
3. **用户能不能看到处理进度、失败原因和重试入口**；
4. **系统能不能抽取合同业务元数据并供业务使用**；
5. **用户能不能对两个版本做比对并消费结果**。

只要这 5 件事还没有闭环，单纯的“技术去耦”就不是完成标准。

### 2.2 项目全局：哪些能力应复用，哪些能力应保留在 app 内

从项目全局看：

1. **文档平台**已经具备 `collection -> documents -> revisions -> processing -> compare-runs` 主链路；
2. **合同管理 app** 不应重新发明一套平行文档处理平台；
3. 但**合同业务字段 schema** 也不应塞回文档平台通用层，而应由 `contract-mgr-v2` 自己定义；
4. 因此本任务的正确方向应是：
   - 复用文档平台的 `collection`、`document`、`processing`、`compare` 能力；
   - 保留合同 app 自己的组织树、合同字段、业务语义、人工确认与运营动作。

### 2.3 当前修复属于什么级别

当前修复：

- **不是小修小补**，因为它影响上传、处理、状态、抽取、比对、权限、运营与审计整条链路；
- **也还不是全局优化完成态**，因为当前还没有真正把文档平台主链路接进 `contract-mgr-v2`；
- 更准确地说，它是一次**必须从产品闭环倒推的中等规模架构收口**。

### 2.4 是否存在最近几轮打转风险

**有，且风险真实存在。**

最容易打转的方式包括：

1. 围绕“路由放哪里”“controller 保不保留”“旧依赖删没删干净”反复讨论；
2. 为 `collection` 绑定、字段抽取、比对展示设计过于复杂的框架；
3. 把应该由用户拍板的事项（如 `collection` 绑定策略、首版必抽字段、比对结果首屏重点）由开发团队自行设计掉。

本轮审计的目标之一，就是把团队从这些打转风险里拉回来。

## 3. 当前整体项目进度判断

### 3.1 当前阶段性质

本任务不是从零开始的新设计，而是对已经进入“独立架构”方向的 `contract-mgr-v2` 做收口治理。当前实际状态可以拆成三层：

1. **方向层**：已经明确 `contract-mgr-v2` 不应再作为 generic autonomous app 混入 `mini-app.service.js` 主路径。
2. **代码层**：已经新增 app 内路由与 `createVersionFromAttachment` 相关实现。
3. **交付层**：任务目录刚建立，审计/变更留痕、边界说明和运行时验证尚未闭环。

### 3.2 当前进度评估

- **已完成部分**：
  - `ContractV2Service.createVersionFromAttachment()` 已实现独立 row_id + content 写入逻辑；
  - 前端已新增 `createVersionFromAttachment()` API 与 store 封装；
  - `ContractList.vue` / `ContractDetail.vue` 已开始切换到新接口；
  - app 内 `server/routes.js` 已新增 `versions/from-attachment` 路由；
  - 本任务已具备 `README.md` / `BRANCH.md` / `changelog_round01.md` / `SELF-TEST.md` / `audit-round01.md` 五件套。

- **未完成部分**：
  - manifest runtime 未声明 `server.routes`，现有 app 内路由不一定会被装载；
  - `contract-v2` 前后端仍是 `/contract-v2/*` 与 `/apps/contract-mgr-v2/*` 混合路径；
  - `collection -> document -> revision -> processing -> compare` 文档平台主链路尚未接入；
  - 专属控制器与 app 内 handler 并存，职责边界不清；
  - 当前尚无“用户可直接消费”的状态闭环、抽取闭环和比对闭环。

### 3.3 综合判断

当前不是方案返工阶段，但也远未达到“可放行”状态。核心问题已经从“要不要独立”进入到“独立链路是否真的成为用户可用、可维护、可运营的主路径”。

## 4. 当前修复方向是否正确

### 4.1 结论

**正确。**

### 4.2 理由

1. `contract-mgr-v2` 使用独立业务表和专属业务语义，这本身就不适合继续挂在 generic `mini_app_rows` CRUD 主链路上；
2. `createVersionFromAttachment()` 的设计把版本建档与 attachment 输入直接闭环，方向符合“app 自己管理业务语义”的当前架构原则；
3. `apps/contract-mgr-v2/server/routes.js` 的出现说明团队已经在向 app 内专属路由装配靠拢，而不是继续堆叠集中式平台控制器；
4. 继续推进的正确目标应是“复用文档平台能力完成合同产品闭环”，而不是只追求“看起来更独立”的代码形态。

### 4.3 当前短板

短板主要在于“过渡态没有收口”且“执行抓手仍偏散”：

1. 新链路已经出现，但是否真的会被 runtime 装配还不成立；
2. 新旧接口并存，但没有明确主次与退役策略；
3. 文档平台能力已知存在，但还没有真正接进合同上传和状态查询主路径；
4. 当前若继续围绕局部技术点修修补补，存在明显打转风险。

## 5. 当前发现的问题与缺口

### 5.1 P0：manifest 未声明 `runtime.server.routes`，app 内路由可能根本不会被运行时挂载

- **级别**：P0
- **位置**：
  - `apps/contract-mgr-v2/manifest.json:10`
  - `lib/app-router-loader.js:36`
  - `lib/app-runtime-loader.js:68`
- **事实**：`app-router-loader` 和 `app-runtime-loader` 只有在 `manifest.runtime.server.routes` 存在时才会装载 app 内路由；但当前 `apps/contract-mgr-v2/manifest.json` 的 `runtime` 仅声明了 `tick` 和 `backup`，没有 `server.routes`。
- **影响**：
  1. `apps/contract-mgr-v2/server/routes.js` 可能只是“存在于仓库中”，但不会实际生效；
  2. 前端新增的 `/apps/contract-mgr-v2/contracts/:id/versions/from-attachment` 调用可能在运行时报 404；
  3. 当前“独立架构已落地”的判断没有运行时证据支撑。
- **判断**：这是当前最关键的阻断项，必须优先解决。
- **技术本质**：代码文件已写，但**运行时装配链未闭合**。

### 5.2 P1：前后端 API 路径仍处于混合态，主路径未统一

- **级别**：P1
- **位置**：
  - `frontend/src/api/contract-v2.ts:88`
  - `frontend/src/api/contract-v2.ts:163`
  - `apps/contract-mgr-v2/server/routes.js:35`
- **事实**：前端大部分 `contract-v2` API 仍调用 `/contract-v2/*`，只有 `createVersionFromAttachment()` 改为 `/apps/contract-mgr-v2/*`；后端 app 内路由则只覆盖 `/apps/contract-mgr-v2/*` 中的局部能力。
- **影响**：
  1. 同一个业务模块同时维护两套路由语义；
  2. 前端、后端、文档都很难判断哪条链路才是未来主路径；
  3. 会持续抬高权限校验、监控、回归测试和后续重构成本。
- **判断**：当前允许过渡，但必须尽快制定“主路径统一计划”。
- **技术本质**：这是**迁移策略未显式化**的问题，而不是单个接口 Bug。

### 5.3 P1：`server/controllers/contract-v2.controller.js` 与 app 内 `server/controllers/version-from-attachment.js` 并存，职责边界不清

- **级别**：P1
- **位置**：
  - `server/controllers/contract-v2.controller.js:163`
  - `apps/contract-mgr-v2/server/controllers/version-from-attachment.js:3`
  - `apps/contract-mgr-v2/server/routes.js:84`
- **事实**：当前既有集中式 `ContractV2Controller.createVersionFromAttachment()`，又有 app 内 `version-from-attachment.js` handler；两者都包装同一个 service 方法，但归属层级不同。
- **影响**：
  1. 业务入口重复，后续变更容易双处修改；
  2. 迁移完成标准不清：到底是保留集中式 controller，还是完全收敛到 app 内 runtime 路由；
  3. 代码审计时难以判断哪一个才是规范实现。
- **判断**：这不是立即阻断运行的故障，但已经是明确的结构性重复。
- **技术本质**：**过渡代码没有定义退役顺序**。

### 5.4 P1：新 app 内 `versions/from-attachment` 路由缺少显式权限控制

- **级别**：P1
- **位置**：
  - `apps/contract-mgr-v2/server/routes.js:84`
  - `apps/contract-mgr-v2/server/controllers/version-from-attachment.js:15`
- **事实**：该接口当前只检查 `userId` 是否存在，没有像 `createContract` / `createNode` 一样挂 `requireAdmin()` 或其它业务权限判断。
- **影响**：
  1. 任意登录用户可能都能为任意合同新增版本；
  2. 与本项目“认证 ≠ 授权，写操作必须校验权限”的规则冲突；
  3. 容易再次重演“资源存在但写权限遗漏”的老问题。
- **判断**：这属于必须优先补上的安全缺口。
- **技术本质**：**新入口把业务闭环打通了，但授权约束还没补齐**。

### 5.5 P1：文档平台主链路尚未真正接入，当前仍停留在“脱离旧链路”的过渡态

- **级别**：P1
- **位置**：
  - `docs/tasks/active/task-20260627-contract-mgr-v2-independence-followup/README.md:60`
  - `server/controllers/doc.controller.js:1440`
  - `server/services/contract-v2.service.js:323`
- **事实**：当前 `contract-mgr-v2` 已开始脱离 `mini_app_rows`，但上传版本尚未真正创建 doc intake，也未稳定建立 `document_id` -> processing -> compare 的文档平台主链路。
- **影响**：
  1. 用户无法真正享受到文档平台的 collection、processing、compare 能力；
  2. 团队可能误以为“去耦完成 = 产品闭环完成”；
  3. 后续状态显示、失败重试、比对复用都会悬空。
- **判断**：这不是单个代码错误，但它是当前产品闭环最大的缺口。
- **技术本质**：**架构方向对了，但主业务流程还没接到现有平台能力上。**

### 5.6 P2：前端仍保留 `newID` / `getDocumentContent` 等跨旧链路依赖，独立化尚未彻底

- **级别**：P2
- **位置**：
  - `frontend/src/components/contract-v2/ContractList.vue:5`
  - `frontend/src/components/contract-v2/ContractDetail.vue:7`
- **事实**：`ContractList.vue` 仍从 `@/api/mini-apps` 导入 `newID`，`ContractDetail.vue` 仍通过 `getDocumentContent(APP_ID, row.row_id)` 读取内容。
- **影响**：
  1. 独立化叙述容易被误解为“完全脱离 old app API”，但事实并非如此；
  2. 后续如果继续推进主链路替换，这些依赖仍需要明确策略。
- **判断**：目前不构成首要阻断，但必须在文档和计划中诚实标注为“仍存在的过渡依赖”。
- **技术本质**：属于**收口未完成**，不是方向错误。

### 5.7 P2：团队存在过度设计风险

- **级别**：P2
- **事实**：本任务后续很容易在以下方向过度设计：
  1. `collection` 多层继承与自动回退策略；
  2. 通用 schema 引擎；
  3. 复杂的 compare 工作台；
  4. 权限抽象框架重构；
  5. 为测试脚本而做模式化抽象。
- **影响**：
  1. 小问题会修很多轮；
  2. 开发团队容易围绕“更优雅的设计”打转；
  3. 用户真正要的首版闭环会被拖慢。
- **判断**：必须在执行单中明确禁止这类展开。
- **技术本质**：这是**执行策略风险**，不是代码 bug。

## 6. 本轮结论

### 6.1 结论等级

**补充变更点继续**

### 6.2 为什么不是“符合标准放行”

因为当前存在至少一个明确 P0：app 内专属路由是否会被 runtime 真正装载尚不成立。且从产品闭环看，文档平台主链路尚未真正接入合同上传主流程，用户还拿不到完整能力。

### 6.3 为什么不是“返工重做”

因为独立化方向本身是对的，且服务层和前端配套已经出现实质性进展；当前问题集中在“主链路接通”和“执行策略收敛”，而不是方案方向错误。

## 7. 本轮执行规则（给开发团队）

### 7.1 审计报告服务执行，不服务讨论

从本轮起，本任务执行单只允许三类事项：

1. **A 类：必须立即修的技术阻断项**
2. **B 类：必须补的产品闭环项**
3. **C 类：必须由用户拍板的决策项**

### 7.2 禁止过度设计

以下事项当前禁止进入执行范围：

1. 通用 schema 引擎
2. 复杂 collection 继承体系
3. 多层权限抽象框架重构
4. 比对结果工作台级复杂交互
5. 为测试脚本“标准化”而做环境变量 / 模式抽象重构

### 7.3 无法判断时的规则

若开发团队无法判断当前设计是否会过度展开、或者无法决定该选哪种产品规则，**必须及时反馈给用户拍板**，不得自行继续扩张方案。

## 8. 新一轮可执行执行单

## A 类：必须立即修的技术阻断项

### A1. 补齐 `manifest.runtime.server.routes`

- **优先级**：P0
- **为什么必须做**：不补这一项，`apps/contract-mgr-v2/server/routes.js` 很可能根本没有被挂载，所有 app 内路由讨论都没有意义。
- **开发动作**：
  1. 在 `apps/contract-mgr-v2/manifest.json` 中声明 `runtime.server.routes`
  2. 启动应用后确认 `AppRouterLoader` 实际挂载 `/api/apps/contract-mgr-v2/*`
  3. 用真实请求验证 `POST /api/apps/contract-mgr-v2/contracts/:contractId/versions/from-attachment` 可访问
- **完成标准**：
  - 不再依赖“文件存在”推定功能已生效；
  - 至少有一条可复现的接口验证记录。
- **技术指导**：
  - 直接复用现有 runtime loader 机制；
  - 禁止新造第三套路由注册方式。
- **是否需要用户拍板**：否

### A2. 给 `versions/from-attachment` 补齐授权

- **优先级**：P0
- **为什么必须做**：这是写操作，不补权限就是安全缺口。
- **开发动作**：
  1. 对齐现有合同创建/编辑权限模型；
  2. 在 app 路由或 handler 中增加写权限判断；
  3. 无权限时返回 403。
- **完成标准**：
  - 非授权用户无法新增版本；
  - 授权用户可正常调用。
- **技术指导**：
  - 先复用已有简单权限模型；
  - 不要为了“完美 RBAC”再开一轮大设计。
- **是否需要用户拍板**：否

## B 类：必须补的产品闭环项

### B1. 明确并实现 `collection` 绑定最小规则

- **优先级**：P0
- **为什么必须做**：没有 `collection`，就没有文档平台主链路，合同上传无法真正进入 doc platform。
- **开发动作**：
  1. 只实现一版最小绑定规则；
  2. 在合同创建页或管理页提供最简单可用的 collection 选择/设置方式；
  3. 把选定结果稳定保存到合同记录或组织节点记录。
- **完成标准**：
  - 用户可以明确知道当前合同会进入哪个 collection；
  - 上传时系统能拿到明确 `collection_id`。
- **技术指导**：
  - 不要一上来实现“组织级默认 + 合同级覆盖 + 类型级继承 + 缺省自动推断”的复杂规则；
  - 若当前无法判断该选哪种模型，立刻让用户拍板。
- **是否需要用户拍板**：是（合同级 / 组织级 / 类型级 三选一）

### B2. 把上传版本改成真正创建 doc intake

- **优先级**：P0
- **为什么必须做**：这是从“过渡态独立代码”走向“文档平台闭环”的关键一步。
- **开发动作**：
  1. 上传附件后调用 `POST /api/docs/intakes`
  2. 传入 `app_id`、`collection_id`、attachment 信息
  3. 记录返回的 `document_id` / `revision_id`
  4. 将 `document_id` 关联到合同记录或版本记录
- **完成标准**：
  - 上传合同后，文档平台里确实有新的 `documents` 记录；
  - 合同详情页能基于 `document_id` 查 processing 状态。
- **技术指导**：
  - 优先复用 doc platform 的 intake，而不是在 `contract-v2.service` 里自己再模拟一套状态机；
  - 若当前还需保留旧 content 表，先作为过渡存储，不要阻塞主链路接通。
- **是否需要用户拍板**：否

### B3. 实现“状态可见”而不是“状态很全”

- **优先级**：P1
- **为什么必须做**：从用户视角，先看到进度比先看到全部技术状态更重要。
- **开发动作**：
  1. 合同详情页展示文档处理状态；
  2. 展示失败原因和可重试入口；
  3. 给技术状态做一层用户可理解的文案映射。
- **完成标准**：
  - 用户能知道当前是“待识别 / 处理中 / 已完成 / 失败”；
  - 错误时知道怎么重试。
- **技术指导**：
  - 不要为了“完美状态机可视化”做复杂流程图组件；
  - 一个状态标签 + 错误提示 + 重试按钮就够作为首版。
- **是否需要用户拍板**：否

### B4. 先落最小元数据抽取字段集

- **优先级**：P1
- **为什么必须做**：没有元数据抽取，合同 app 只是文档上传壳，不是合同管理。
- **开发动作**：
  1. 先定义最小通用字段集；
  2. 再定义最小销售专属字段集；
  3. 抽取结果回填业务表；
  4. 页面允许人工确认 / 修改。
- **完成标准**：
  - 至少一版通用字段和一版销售字段可抽取、可落库、可人工修正。
- **技术指导**：
  - 先做字段表，不做动态 schema 引擎；
  - 先做单次抽取结果确认，不做复杂审批流。
- **是否需要用户拍板**：是（最小字段集范围）

### B5. 先把比对能力接到合同页，不做复杂工作台

- **优先级**：P1
- **为什么必须做**：文档平台 compare 能力已经存在，当前更需要接入，而不是重新发明。
- **开发动作**：
  1. 在合同详情页选择两个版本；
  2. 调用 `/api/docs/compare-runs` 发起比对；
  3. 读取 run 结果并展示摘要 + 明细。
- **完成标准**：
  - 用户可从合同页发起一次比对；
  - 可查看结果；
  - 结果来自文档平台持久化记录。
- **技术指导**：
  - 首版先做“摘要 + 明细列表”；
  - 不做复杂 diff 工作台、风险评分体系、批量比对中心。
- **是否需要用户拍板**：是（首版最看重的结果维度）

## C 类：必须由用户拍板的决策项

### C1. `collection` 绑定模型

- **为什么不能自行设计**：这会直接影响权限、迁移、召回范围和后续运营模型。
- **需要用户给出的最小决策**：
  - 先选一种：合同级 / 组织级 / 类型级。
- **开发团队禁止事项**：
  - 禁止在未确认前实现多层继承和自动回退算法。

### C2. 销售合同最小抽取字段集

- **为什么不能自行设计**：集团、项目、零件号哪些是必须，哪些只是“未来可能有用”，只有业务方知道。
- **需要用户给出的最小决策**：
  - 首版必须抽哪些字段。
- **开发团队禁止事项**：
  - 禁止把字段系统设计成通用低代码字段引擎再开始开发。

### C3. 比对结果首版展示重点

- **为什么不能自行设计**：用户真正关心的是条款变化、业务字段变化还是风险提示，优先级必须由产品 owner 定。
- **需要用户给出的最小决策**：
  - 首版优先展示什么。
- **开发团队禁止事项**：
  - 禁止先做复杂对比工作台。
