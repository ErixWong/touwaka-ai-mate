## 4. 本轮新发现的问题和缺口

### P1

#### P1-1 `ContractDetail.vue` 仍存在多处新增用户可见文本未走 i18n

- **证据**：`frontend/src/components/contract-v2/ContractDetail.vue:341`、`frontend/src/components/contract-v2/ContractDetail.vue:482`、`frontend/src/components/contract-v2/ContractDetail.vue:554`、`frontend/src/components/contract-v2/ContractDetail.vue:687`、`frontend/src/components/contract-v2/ContractDetail.vue:791` 等位置仍直接写入中文文案。

- **影响**：
  1. 详情页中英双语一致性被破坏；
  2. 后续继续在此组件叠加功能时，硬编码文本会持续扩散；
  3. 会让“功能已收口”的页面在标准化审查中继续卡住。
- **优先级理由**：不阻断主链路运行，但会阻断按项目标准放行，且修复成本低，适合当前阶段收尾。

### P2

#### P2-1 API 语义上仍保留一个未使用/易混淆的 `triggerMetadataExtract()` 定义

- **证据**：`frontend/src/api/contract-v2.ts:219` 的 `triggerMetadataExtract()` 与 `extractMetadata()` 指向同一路径 `/versions/:versionId/extract-metadata`，而 `server/services/contract-v2.service.js:937` 的 `triggerMetadataExtract()` 当前没有对应路由实际使用。
- **问题性质**：属于接口语义漂移/死代码征兆，不是当前运行时 bug。
- **影响**：后续若团队再补“触发处理”和“直接提取”两种能力，容易误以为当前接口已区分，增加维护歧义。
- **优先级理由**：不影响当前可用性，但建议在正式放行前做一次极小清理或文档澄清。

## 6.5 对本轮审计方法的复盘（给开发团队与负责人看）

### 6.5.1 这轮审计有没有从第一性原理出发

**结论：有，而且本轮判断基本回到了“用户真正要完成什么动作”这个最小业务事实。**

本轮不是沿着“哪里还有格式不统一、哪里还能再抽象一下”这种表层路径继续扩写，而是先回到两个基础问题：

1. **用户当前最关心的动作是否已经闭环**
   - 对这个任务来说，用户真正要完成的是：
     - 上传版本；
     - 针对某个版本提取 metadata；
     - 对两个版本发起 compare；
     - 能在页面上真实触达到这些动作。
   - round07 修完后，这三条主动作已经从 document 维度误判断切回 revision 维度事实。

2. **当前剩余问题是不是还在破坏这个最小业务事实**
   - compare 入口阻断、提取按钮隐藏，这类问题会直接破坏用户动作闭环，所以必须优先修；
   - i18n 硬编码、未使用 API 命名歧义，不会直接破坏主链路，它们属于“标准化/可维护性尾项”，不应与主阻断混成同一优先级。

因此，这轮审计的核心不是“继续找还能修什么”，而是判断：**主业务事实是否已经成立，剩余项是否值得继续在本轮投入。**

### 6.5.2 这轮审计有没有站在项目全局考虑

**结论：有，但全局视角控制在必要范围内，没有把问题无谓升级成大重构。**

本轮全局视角主要体现在：

1. 不是只看 `createCompareRun()` 单点，而是联动核对了：
   - `server/services/contract-v2.service.js`
   - `lib/doc-compare-executor.js`
   - `frontend/src/components/contract-v2/ContractDetail.vue`
   - `SELF-TEST.md`

2. 不是只看“代码能不能跑”，而是同时看：
   - 主业务语义是否一致；
   - 前后端入口是否一致；
   - 文档是否会误导下一轮继续打转；
   - 哪些问题真影响用户，哪些只是工程尾项。

3. 没有把问题扩大成：
   - compare 算法重做；
   - revision 状态服务重构；
   - 新增复杂前端可提取状态推导；
   - 为了“更优雅”再抽一层公共抽象。

这说明本轮审计有全局视角，但没有脱离当前任务边界。

### 6.5.3 当前修复属于小修小补，还是全局优化

**结论：这轮已完成的修复，不是零散小补；更准确地说，是“围绕全局语义做最后一跳收口”。**

原因如下：

1. **不是小修小补**
   - compare 入口与提取入口，都是用户主链路；
   - 修的是“版本=revision级对象”这个全局业务语义能否真正落到最后一跳。

2. **也不是全局重构**
   - 没改数据库；
   - 没改 compare 算法；
   - 没新增状态机；
   - 没引入新抽象层。

3. **本质上是小范围、强约束的全局语义收口**
   - 已拍板方向是全局性的；
   - 实际执行是定点性的；
   - 这是当前阶段最合适的修法。

### 6.5.4 最近几轮有没有在反复打转

**结论：前几轮有轻度打转，本轮已明显收敛；但如果继续把低价值尾项当主问题追，会再次进入“后期打转”。**

#### 已摆脱的打转

1. 不再停留在 DTO 字段错误、旧入口旁路、文档乐观表述这类浅层补洞。
2. round06、round07 已把最关键的 revision/document 语义错位逐步收口到 metadata、compare、前端入口三处主链路。

#### 当前仍需警惕的打转模式

1. **主链路问题已基本解决，但团队可能继续围绕低价值标准项多轮修补**；
2. **把 i18n、命名清理、未使用 API 等尾项，错误抬升为“阻断主链路”的问题**；
3. **为了消灭轻度重复逻辑，再次引入 helper / 状态层 / 额外接口设计，造成过度设计。**

#### 给开发团队的执行提醒

- 当前不要再把“还有一些工程尾项”理解成“还能继续深挖几轮”；
- 这轮之后的原则应该是：
  - 主链路相关问题继续修；
  - 低价值尾项尽量一轮并掉；
  - 不允许为低价值问题再开复杂设计。
